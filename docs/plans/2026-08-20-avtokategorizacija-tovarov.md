# Автоматическая категоризация товаров чека

**Дата:** 2026-08-20
**Статус:** согласован в обсуждении, к реализации

## Цель

Товар из чека ФНС получает настоящую товарную категорию без участия человека. Пользователь не подтверждает чек: отсканировал QR — чек проведён, категории проставлены. Человек только исправляет ошибки, и каждое исправление запоминается.

## Как это работает

```
QR → ФНС → чек проведён и виден
                ↓
     сопоставление названия (закреплённое человеком)
                ↓
     похожие названия из истории пользователя
                ↓
     внешняя модель по OpenAI-совместимому API (отдельной задачей)
                ↓
     «Прочее», если ничего не подошло
```

Первые три ступени выполняются в той же celery-задаче, что обрабатывает чек, — категории видны сразу. Четвёртая ступень (внешняя модель) идёт отдельной задачей: чек не должен зависеть от доступности внешнего сервиса.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Счёт списания | Уже выбирается на вкладках «Сканировать QR» и «Файл» — повторный вопрос убирается |
| Расхождение сумм | Не блокирует проведение; чек помечается требующим внимания с указанием причины |
| Нехватка средств | Не хранится, вычисляется при отображении |
| Товарная категория | Запись справочника пользователя, строка чека ссылается на неё |
| Справочник | Свой у каждого пользователя, плоский, без вложенности |
| Пополнение справочника | Автоматическое, с проверкой на непохожесть; категории-близнецы выносятся на объединение |
| Подбор по близости | `pg_trgm` по написанию плюс векторы в pgvector по смыслу |
| Что сравниваем | Ближайшие уже размеченные товары пользователя, не название категории |
| Модель эмбеддингов | Отдельный контейнер с HTTP API, вне процесса celery |
| Внешняя модель | Выключена по умолчанию; включается своей переменной, не общей с выписками |
| Формат ответа модели | `response_format: json_schema`, требование зафиксировано в документации |
| При отказе внешней модели | Два повтора с задержкой, затем «Прочее» |
| Названия провайдеров | Не упоминаются ни в коде, ни в переменных, ни в тикетах, ни в коммитах |

Зафиксировано в ADR-0005 (проведение без подтверждения), ADR-0006 (справочник категорий), ADR-0007 (pgvector и тесты на Postgres). Термины — в `CONTEXT.md`, раздел «Товарные категории».

## Тикеты

### 1. Нормализация накопленных категорий

Не требует кода. По приложению ниже свести 62 существующие категории к целевому справочнику, вычитать и утвердить таблицу соответствий. Отдельно решить судьбу зонтичной категории «Продукты питания» (32 товара) — она пересекается со всеми остальными.

**Готово, когда:** таблица соответствий утверждена и лежит в репозитории рядом с этим планом.

### 2. Справочник товарных категорий

Модель товарной категории (пользователь, название, нормализованное название с ограничением уникальности). У товара — ссылка на категорию и признак источника: перенесено, подобрано по близости, получено от внешней модели, поставлено человеком. Миграция переносит 286 существующих товаров по таблице из тикета 1 с источником «перенесено». Сид справочника для новых пользователей — из целевого списка. Категория «Возврат оплаты» не переносится: тип операции уже хранится в чеке.

**Зависит от:** тикет 1.
**Готово, когда:** ни у одного пользователя нет двух категорий с одинаковым нормализованным названием.

### 3. Проведение чека без подтверждения

`PendingReceipt` заменяется журналом обработки: статус, ошибка, идентификатор задачи, ссылка на созданный чек, дедупликация по фискальному ключу и хешу изображения, повторные попытки. Разобранные данные в журнале не хранятся — чек создаётся сразу. Экран проверки чека и его форма удаляются. У чека появляется причина, по которой он требует внимания; она пересчитывается при каждом сохранении в редактировании чека и исчезает, когда расхождение устранено. После сканирования пользователь остаётся на странице сканера и получает уведомление со ссылкой на чек.

**Зависит от:** ничего, можно вести параллельно с тикетом 2.
**Готово, когда:** чек появляется в списке без единого действия пользователя после сканирования.

### 4. Тесты на Postgres

`USE_DB_FOR_TESTS` перестаёт быть опциональным: Postgres поднимается в CI и локально. Ожидается, что часть тестов упадёт — до сих пор они шли на SQLite и не проверяли `GinIndex` и полнотекстовый поиск с русской конфигурацией.

**Зависит от:** ничего.
**Готово, когда:** весь набор тестов зелёный на Postgres, SQLite из тестовой конфигурации убран.

### 5. Подбор категории по близости названия

Контейнер с моделью эмбеддингов и HTTP API. Расширения `pg_trgm` и `pgvector`. Хранение вектора названия товара. Ступени: закреплённое сопоставление названия, затем совпадение по написанию через триграммы, затем ближайшие размеченные товары пользователя по вектору. Пороги настраиваются. Старые правила `_CATEGORY_RULES` перестают быть классификатором — они уже стали основой справочника и как второй источник истины о категориях больше не нужны.

**Зависит от:** тикеты 2 и 4.
**Готово, когда:** на выгрузке из 172 названий замерена доля правильных попаданий по каждой ступени отдельно.

### 6. Внешняя модель на остатке

Транспортный клиент OpenAI-совместимого API переезжает в `core/`, доменные запросы остаются в своих приложениях. Настройки чеков (`RECEIPT_CATEGORY_LLM_*`) отделены от настроек выписок (`CATEGORY_CLASSIFIER_*`); тест падает, если подсистемы читают одну переменную. Модель получает название товара и справочник пользователя, отвечает по json-схеме: категория из справочника либо предложение новой. Предложенная категория создаётся, только если достаточно не похожа на существующие. Вызов идёт отдельной задачей, два повтора, затем «Прочее».

**Зависит от:** тикет 5.
**Готово, когда:** при незаданной переменной система работает целиком на локальных ступенях.

### 7. Категории-близнецы

Периодическая задача ищет пары категорий, обозначающих одно и то же, и показывает их пользователю списком «объединить / оставить». Объединение переносит товары и удаляет лишнюю категорию.

**Зависит от:** тикет 6.

### 8. Запоминание исправлений

Правка категории человеком закрепляет сопоставление названия: оно имеет приоритет над всеми ступенями подбора и больше не пересчитывается. Все товары пользователя с тем же названием переклассифицируются задним числом.

**Зависит от:** тикет 2.

## Открытые риски

- **Две трети названий уникальны** (`pct_seen_once = 68.6%`), поэтому кэш повторов даёт около 30% экономии, а не 80%. Основная нагрузка ложится на подбор по близости и внешнюю модель — их качество важнее, чем ожидалось изначально.
- **Кассовые сокращения.** `С/К КОЛБ.БРАУНШВ.` — не естественный текст, и сравнение с названием категории на таких строках работает плохо. Схема опирается на сравнение с ранее размеченными товарами, где написание такое же; при пустой истории подбор по близости бесполезен и всё уходит во внешнюю модель.
- **Порог непохожести не ловит смысл.** «Готовая продукция» и «Быстрое питание» не похожи ни по написанию, ни, скорее всего, по вектору. Такие пары ловит только тикет 7, и то с участием человека.
