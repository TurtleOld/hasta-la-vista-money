## Категории расхода из банковских выписок создаются из сырых описаний мерчанта

**Что происходит.** При импорте выписки каждой строке нужна категория расхода. Имя категории берётся прямо из описания операции в PDF, без какой-либо обработки, поэтому в справочнике появляются категории вида `SUPERMARKET SPAR NOVOSIBIRSK 1234` — по одной на каждый терминал.

**Почему так.** В PR #861 (коммит `41d591c4`, июнь 2026) для этого был добавлен LLM-классификатор: он превращал сырое описание в осмысленное название категории, а перед отправкой применялся `strip_pii`. Механизм выключается пустой переменной `CATEGORY_CLASSIFIER_BASE_URL`, и она оставлена пустой сознательно — чтобы описания контрагентов не уходили во внешний сервис. В результате классификатор не работает, а исходная проблема вернулась.

**Что стоит сделать.** Автокатегоризация товаров чеков (см. план `docs/plans/2026-08-20-avtokategorizacija-tovarov.md`) строит механизм «справочник + подбор по близости названия + внешняя модель только на остатке». Его локальная часть — подбор по близости — не отправляет наружу ничего и решает ту же задачу для выписок. После завершения работ по чекам механизм имеет смысл перенести на категории расхода.

**Важно при переносе.** Настройки внешней модели у чеков и у выписок разведены намеренно (`RECEIPT_CATEGORY_LLM_*` против `CATEGORY_CLASSIFIER_*`). Сливать их обратно в одну переменную нельзя: включение внешней модели для товаров чека тогда молча включит отправку описаний контрагентов из выписок.

**Что именно утекает, если включить `CATEGORY_CLASSIFIER_BASE_URL`.** Суммы, даты, балансы и номера счетов не отправляются — в запрос уходит только очищенное описание операции, её тип и список имён категорий пользователя. Но описание — это название контрагента, и по потоку таких описаний видно, где человек тратит. Кроме того, в `strip_pii` есть пробел: маска карты вида `**** 1234` не подпадает ни под один из трёх шаблонов и проходит как есть.

## `process_bank_statement` — мёртвый код, покрытый тестами

**Что происходит.** Функция `process_bank_statement` в `hasta_la_vista_money/users/services/bank_statement.py:1195` в продакшне не вызывается: страница загрузки выписки запускает celery-задачу `process_bank_statement_task` из `users/tasks.py`. Единственный, кто вызывает старую функцию, — тесты (`users/tests/test_bank_statement_upload.py`, класс интеграционных тестов с `:2769`).

**Почему это плохо.** Пути расходятся по поведению: живой применяет `strip_pii` и классификатор категорий, мёртвый передаёт сырое описание напрямую в `_get_or_create_category`. То есть набор зелёных интеграционных тестов проверяет поведение, которого в работающем приложении нет.

**Что стоит сделать.** Удалить функцию и перевести её тесты на `process_bank_statement_task` либо на сервис, который задача вызывает.
